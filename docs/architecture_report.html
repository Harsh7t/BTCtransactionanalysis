1 · What the system is for

Commercial chain-analysis tools are a purchasable, solved product. None of them ingest packet capture, because a private company cannot lawfully tap an ISP. That capability gap is the reason this problem statement exists.

Every blockchain tool can tell you that money moved suspiciously. This one correlates the network layer — source IP, port, arrival timestamp — with the chain layer — TXID, addresses, amounts — to say who moved it, and refuses to answer when the evidence is shared infrastructure.

The deployment context decides the architecture

The target is an air-gapped analyst workstation. That single constraint explains most of the engineering choices, and each one is a rejection of a more fashionable option:

ChoiceRejected alternativeReason
DuckDB, a filePostgreSQLA service that must be installed, started and kept alive on a machine with no network.
igraph, in memoryNeo4jNo analytical gain at this scale, and a second service to die mid-demo.
FastAPI in the same process as the modelsA model-serving sidecarNo serialisation boundary, nothing to orchestrate.
Bundled DB-IP Lite ASN databaseA GeoIP web APIAny lookup that leaves the machine breaks the entire premise.
Gradient-boosted treesGraph neural networkMeasured: see §6. SHAP is exact for trees.
The offline claim is enforced, not asserted. make offline-check greps the whole application package for https?:// and fails the build on a match. It cannot tell a citation from an endpoint, so URLs live in documentation and never in code. The container is additionally verified under --network none.

Degrade, never fail. If a stage raises, the run continues and the interface reports that component as unavailable. A stack trace in front of an analyst is the one unacceptable outcome, and a partial answer with an honest gap is more useful than no answer at all.

4 · How one transaction is analysed

The stages above describe the machinery. This is what actually happens to a single row of the capture, from the byte that arrives to the sentence an analyst reads.

Why not score transactions directly? A transaction has almost no behaviour — it has amounts and a timestamp. Laundering is a pattern over time: peel chains, rapid layering, structuring. Those are properties of an actor across many transactions, which is why the primary model works at the actor level and reaches PR-AUC 0.2998, while the transaction head reaches 0.0726 against a 0.0015 base rate. Both are reported; neither is hidden.

5 · Where the AI is

Five learned components, each doing a job that cannot be written as a rule. Every one is trained, versioned and recorded in the manifest — and the ablation in §10 proves that the lift comes from them and not from the rules beside them.

Answering the question directly

The AI is not a wrapper around a rules engine, and this is checkable rather than asserted. The ablation below is a row-by-row build-up of the shipped system, and each row is an entry in metrics.json → ablation:

The base rate on this fold is 0.0039. Rules alone land below it. Everything above the base rate is contributed by the learned components — which is precisely what the problem statement's "a working model, not just rules" asks to be demonstrated.

A measurement that overturned our own design. The system originally fused three signals into one ranking score at 0.85 supervised / 0.05 novelty / 0.10 evidence. That survived the demo profile and collapsed at a realistic base rate: PR-AUC fell from 0.2803 to 0.1644 at only 5% novelty weight and to 0.0561 at 20% — 41% of the ranking lost for the first five points alone. The evidence term carries no ranking signal at 0.39% positives, and being near-binary it promoted a broad band of unremarkable actors above genuinely suspicious ones. Ranking is now the classifier's job alone — 1.00 / 0.00 / 0.00. Coverage of unlabelled typologies is bought differently: 8 of the 60 queue slots are reserved for the highest-novelty actors the classifier did not surface. Blending corrupts every rank; reserving costs exactly the slots it uses. Full sweep in metrics.json → fusion_sweep.

Why these models, and what was rejected

ModelJobWhy this one
Node2Vec (64-d)Structural rolesNobody labels "mixer-like topology". The embedding discovers it, and it runs CPU-only.
Gradient-boosted treesPrimary classifierBest-in-class on tabular data, and SHAP is exact for trees rather than approximated.
IsolationForestNoveltyLinear-time, no distance assumptions. Answers "what about patterns you never labelled?"
HDBSCANBehavioural archetypesDoes not need k, and explicitly labels noise — which is what an outlier is.
Isotonic regressionCalibrationNon-parametric, so it corrects arbitrary miscalibration shapes rather than an assumed one.
Graph neural networks were rejected on evidence, not taste. Weber et al. (2019) found tree ensembles outperformed a GCN on illicit-class F1 on exactly this task. GNNExplainer output is hard to turn into analyst-readable prose, and a GNN is likelier to memorise generator fingerprints — a real risk when the training data is synthetic. The structural signal a GNN would learn is captured instead by the Node2Vec features, whose contribution is measured separately in the ablation (+0.026 PR-AUC on bulk, +0.114 on demo). Closed-form message passing over the payment graph — the part of a GNN that carries signal, with no deep-learning dependency and exact SHAP kept — was also built and measured. It lowered PR-AUC, and was removed.

7 · Training data and splits

No dataset was provided, and no public dataset has a network layer. So "collection" meant writing a defensible simulator — 1,701 lines, seeded, versioned — and then attacking it harder than a reviewer would.

The leak test — and the two defects it caught

We wrote the generator, so we know the answers, so every accuracy number is self-referential. A sharp reviewer attacks the data, not the model. So the build gates on a test that trains a classifier only on fields with no constructed path to the label, and requires it to score at the base rate.

It has earned its keep twice, and both catches are the kind only this test finds:

  1. Crime proceeds were drawn from a different amount distribution than licit payments — a 1.7× shortcut. Fixed: proceeds now use the same payment-size distribution, with the archetype controlling count and dispersion, never absolute scale.
  2. Mule wallets drew their operating system from a different distribution than everyone else — 1.2× on ephemeral-port features. The model was reading "no BSD hosts" as evidence of laundering.

Reproducible from the seed — and the defect that said otherwise

A published number is worth something only if someone else can regenerate it. The generator was documented as deterministic and was not: it chose an actor's announcing IP with Python's built-in string hash(), which is randomised per process. Two runs at the same seed agreed on every column except src_ip — the network half of the thesis. It now uses zlib.crc32, the figures in this document were regenerated after the fix, and tests/test_determinism.py checks the property across a process boundary, because inside a single process the bug is invisible.

Validated against real Bitcoin, not only our own data

Because the synthetic set is ours, the chain-side detector is additionally validated on real labelled Bitcoin. This proves nothing about the network layer — Elliptic has no IP data — and the document says so rather than blurring the two.

Using the 77% of Elliptic everyone discards — measured, not adopted

Elliptic leaves 77% of its transactions unlabelled, and published work — including the baseline above — drops them. Positive-Unlabelled learning (Elkan & Noto, 2008) is the principled alternative: estimate how likely an illicit transaction was to be labelled at all, then re-weight the unknowns instead of discarding them. detect/pu.py implements it and eval/external.py compares it on the same temporal split.

It loses wherever the top of the ranking matters. The estimate explains why: c = 0.9157, meaning roughly 92% of illicit transactions are already labelled, so the unknown pool is nearly all licit and there is little to recover. It is not used on the synthetic data at all — the generator knows every label, so c = 1 by construction. Keeping the simpler method is now a measurement rather than a convention.

8 · Attribution — the network ⇄ chain correlation

The component that answers the problem statement's load-bearing verb. Given an on-chain actor, which network identity is behind it — and how sure are we, honestly?

The problem it has to solve. Naive attribution says "whoever we saw announce it first is the originator". Koshy et al. (FC 2014) and Biryukov et al. (CCS 2014) showed P2P relay patterns leak origin — and Bitcoin Core responded. Modern diffusion applies an independent randomised delay per peer, so the first announcement any collector observes is frequently a relay, not the source. First-seen attribution has therefore been wrong since 2015. This engine models the defence instead of ignoring it.
①
entity × IP co-occurrence matrix
How often each actor was seen announcing from each IP, counted across every announcement in the capture — not the first one.
 engine.py
②
propagation-tree roots, per transaction
src_ip → dst_ip edges with timestamps reconstruct who announced to whom. A node that announces but is never announced to within that transaction is a root — materially stronger evidence than “seen first”. Where no candidate survives, the transaction contributes no root evidence at all. Most designs ignore dst_ip entirely and cannot do this.
 diffusion.py
③
hypergeometric significance vs a null model
A busy relay co-occurs heavily with everyone. The real question is whether the association is stronger than chance given how much traffic that address carries and how many transactions that actor made. Benjamini–Hochberg FDR control is applied across the whole pair set at α 0.01 — testing hundreds of thousands of pairs at an uncorrected p < 0.01 would hand back thousands of spurious links.
 significance.py
④
infrastructure classification and penalty
Two independent sources, because either alone is exploitable: the declared ASN type from the bundled database, and the observed number of distinct actors announcing from that address in this capture.
 infra.py
⑤
behavioural timezone inference
People keep hours. Which UTC offset makes this actor's activity histogram look most like a human waking, working and sleeping? Derived from behaviour, not from the GeoIP database — so when the two independent methods agree, that is real corroboration. A flat 24/7 histogram fits every offset equally and is reported as such.
 behaviour.py
⑥
confidence, interval, counterfactuals
The product of everything above. Where every candidate is shared infrastructure, the attribution is suppressed rather than reported at a confidence that would mislead. An attribution engine that always produces an answer is not an attribution engine.
 confidence.py

Table 2. The attribution engine, six steps, one module each. The counterfactuals in step ⑥ are computed by re-running this same model with one input changed — so they are a property of the model, not authored text.

confidence =
statistical strength  ×  repeat-observation weight  ×  propagation-root bonus
           ×  infrastructure penalty  ×  timezone corroboration
Repeat-observation weight saturates as 1 − e−n/4: one sighting earns ~22% of full weight, eight earn ~86%. One sighting can never on its own produce a confident attribution — which is exactly the defence randomised diffusion provides.

9 · Explainability

Four layers, because "explainable" is a graded deliverable and not garnish. Each answers a different question an analyst actually asks.

Stated openly: explanation faithfulness is not measured. SHAP values are shown to analysts, but no deletion or insertion test proves the highlighted features actually drive the prediction. This is the one item from the original plan that was never built, and it is recorded as an open item rather than quietly omitted.

What the ranking figures measure

Every ranking figure here scores the order an analyst is actually shown, which is not the same as scoring the calibrated probability. Isotonic calibration is a step function that clusters near its 0.97 ceiling, so the queue ranks on the raw fused score at full resolution, uses value moved only to break an exact tie, and lets the calibrated probability do the two jobs it is good at: gating the queue at 0.75, and being displayed.

Why the late fold is harder — censoring, not drift

Discrimination falls across the temporally forward splits: bulk ROC-AUC is 0.9977 on train, 0.9565 on calibration and 0.7072 on test. The base rate falls with it, but ROC-AUC does not depend on the base rate, so something about the late fold is genuinely harder. Two explanations predict different shapes. Drift — the model ageing — predicts a flat deficit. Right-censoring predicts recovery as observation time grows: a capture ends, so an actor first seen a week before the end has only a week of behaviour to describe it, and a temporally forward split puts exactly those actors in the test fold. eval/diagnostics.py stratifies the fold to tell them apart.

Monotone in the observation window on both profiles: it is censoring. On bulk the automated verdict in metrics.json reads indeterminate, because its primary check — actors still active in the final 24 hours — has only two members there; the quartile stratification is the evidence, and it replicates. Actors that never sent a transaction score at chance (ROC-AUC 0.490 on demo, 0.497 on bulk), because almost every feature is sender-side: a low score on such an actor means unranked, never cleared.

Five features normalise each aggregate by the window that was actually available. They are worth +0.042 PR-AUC on demo (0.4323 → 0.4746) and −0.004 on bulk (0.2772 → 0.2734) — a gain on one profile and a wash on the other, reported both ways. The raw window length is deliberately not a feature: the generator front-loads campaigns, so calendar position would teach the model that late means licit. The leak test passes with the correction in place.

What makes every number in this document checkable

Each run writes a provenance receipt: the input file's SHA-256, the seed, the feature version, the model backend and the git commit. The trained artefacts carry the same. The container build additionally re-derives the host's score fingerprint inside Linux and fails the build if it drifts — because the container installs scikit-learn 1.7.2 while the shipped artefacts were pickled by 1.9.0, and "the scores are bit-identical" is a fact about two specific versions rather than a property of the design.

12 · The analyst interface

The interface is what an analyst actually uses: one offline process serving both the API and the built React application, opening in the light theme. It is organised around a single question — which of these leads do I open first, and why is each one here?

ScreenRouteWhat it is for
Landing/The thesis, a drop zone for a capture, and three bundled samples (judge, demo, bulk). The live diffusion field behind it draws the problem the system solves: a peer announces a transaction and the rest relay it after randomised delays.
Scoringwhile a run is activeThe nine stages as a track, each explained in plain and technical language while it runs.
Alert queue#/alertsThe ranked leads — described below.
Case file#/case/{entity}The investigative document for one lead: assessment, calibrated confidence, what would change it, SHAP attributions, network attribution, link analysis, activity timeline, evidence chain with real TXIDs, HTML export, confirm and dismiss.
Model#/modelScorecard, ablation, reliability diagram, held-out typologies, leak test, real-data validation, attribution against coverage, resolution quality, failure gallery, feature importance, split integrity.
Provenance#/provenanceThe run manifest — input SHA-256, seed, feature version, backend, git commit — plus ingest integrity and per-stage timings.

The alert queue

The queue opens on the reduction the system exists to produce — rows ingested, actors resolved, ranked leads — with the ingest receipt one click away rather than occupying the screen. Every lead then carries three evidence marks: chain when a named typology corroborates it, network when the attribution engine named an IP, and model for the classifier's own call or a reserved novelty slot. On a demo-profile run in data/case.duckdb, 41 of the 60 leads carry a typology, 3 carry a resolved network identity and 8 occupy novelty slots.

LayoutOptimised forWhat each lead shows
tableComparing a value down a column across all sixty leads. The default.Rank, evidence marks, entity with address · transaction · IP counts, pattern, attribution, confidence with its interval, novelty, and value moved with a log-scaled magnitude bar. Numeric columns sort.
dossierReading the queue in order.Rank in the margin, entity as a heading, the written narrative with its announcing-host sentence set apart in the network colour — the part that differs from lead to lead — then figures and attribution.
focusOne lead at a time, with someone watching.The lead at presentation size; a strip of all sixty leads coloured by evidence, clickable; narrative; figures; the five SHAP drivers; attribution; evidence chain with TXIDs; the link-analysis graph beside it; confirm and dismiss.

Controls: / focuses search, j / k or the arrow keys move, Enter opens the case file. Filters cover typology, host class and unreviewed leads; a confidence-threshold slider states how many leads it shows and how many it suppresses; an entities / transactions switch exposes the transaction-level head. Confirm and dismiss post to /api/alerts/{entity}/verdict and adjust only the next run's presentation order — dismissed −0.25, confirmed +0.10 on the ranking score. They never retrain the model, so a triage tool cannot quietly learn one analyst's habits.

Link analysis

The server extracts a k-hop subgraph with a hard 1,500-node cap and says when it has capped. Positions are computed directly rather than by a force-directed layout, so a case draws the same way every time, and every visual channel carries data.

ChannelEncodes
RingHop distance from the subject, which sits at the centre.
SideLeft: counterparties the subject received value from. Right: counterparties it sent value to. A branch keeps the side of the first hop that created it.
Position on an arcValue rank — the largest flows sit on the horizontal axis.
Node size and hueAlert score, stretched over the run's observed range so the colour means the same thing on every case file.
Edge widthLog of value moved, because values span several orders of magnitude.
Marching dashesThe traced path, moving in the direction the money moved. Off under reduced motion.
Time scrubberReplays edges in the order they first carried value, labelled with the real timestamp. Edge timestamps are stored in entity_edges; a run recorded before they were gets no scrubber rather than a broken one.

Hovering a node isolates its neighbourhood; clicking an actor traces its path back to the subject and offers its case file; the hop control switches between one, two and three hops; and wallets adds the subject's own addresses and transactions as membership links.
